# 盘迹 PanTrace · 群分享采集插件

在 AstrBot（QQ 官方机器人 / NapCat-OneBot）里**静默采集**指定群中群主、管理员发的网盘分享，整理后上报给盘迹 PanTrace 后端入库。

**本插件不发命令、不回复、不拦截消息。** 装上去之后群里看不出有机器人——除非你把「采集后回执」打开。

## 它做什么

```
                             ┌─► 大模型结构化（并发 3，阈值自适应）
群消息 ──► 三道闸门 ──► 入队 ─┤
                             └─► 常驻发送器（500ms 一节拍）──► POST /api/ingest/qq ──► 入库
```

三道闸门依次是：

1. **群白名单** —— 不在 `capture_groups` 里的群，整条消息直接跳过
2. **人或身份** —— 在 `capture_senders` 里的人不看身份照收；其余人只采群主/管理员（`raw_message.sender.role`）
3. **域名粗筛** —— 消息里没有网盘域名就完全不上报，闲聊连一次 HTTP 都不发

过了三道闸门才会进队列。**发送不靠"下一条消息"驱动**：插件里有一个常驻发送器，按 500ms 的节拍自己看队列，把准备好的消息成批发走（单次最多 40 条）。刚进队列的消息先攒 1 秒，连着发的几条能合成一次 POST；队列里已经堆了 8 条以上就不再攒。

「准备好」= 模型给出结论了，或者等满等待阈值（`ai_settle` 是下限，实际阈值按模型近期耗时自动放大，见下）。**结构化再慢也不会挡住上报**，两条流水线各跑各的。

队列上限 500 条。真顶到上限（意味着后端长时间不可达）会丢最老的并**明确打一行 WARNING**，不会静默截断。

## 插件不干的事（以及为什么）

- **不解析链接、不猜标题。** 链接正则和标题规则只在后端存在一份（`search/clean.py` + `qq_intake.py`）。插件再写一套，两边迟早对不上，而且是那种「群里能认、表格导入认不出」的隐蔽偏差。
- **不做搜索。** 这是刻意的：搜索是用户主动发命令，采集是后台静默跑，两者对事件的处理方式、出错后的表现、日志噪声完全不同，混在一个插件里排查问题会互相干扰。搜索走网站。
- **失败不影响群聊。** 采集链路所有异常都吞掉记日志，不上抛。上报失败按 2s / 5s / 10s 退避重试三次；仍失败就放回队列，等冷却后重来（不丢）。队列真顶到上限才丢最老的，而且会打日志。

## 安装

1. 把插件目录（或 `astrbot-plugin-pantrace.zip`）丢进 AstrBot 的 `data/plugins/`
2. 重启 AstrBot，或在 WebUI「插件」页点重载
3. 填配置，见下

依赖：`aiohttp`（AstrBot 自带）。

## 配置

WebUI → 插件 → 盘迹群分享采集。

| 项 | 默认 | 说明 |
|---|---|---|
| PanTrace 服务地址 | — | **必填**。后端根地址，不带结尾斜杠 |
| 群消息采集 | 关 | 总开关。关着时插件不监听任何消息 |
| 监听的群号 | 空 | 群号纯数字，可填多个。**必须填**：留空则一条都不采 |
| 采集哪些身份 | owner, admin | 见下 |
| 额外采集指定的人 | 空 | 填 QQ 号，不看身份照收。见下 |
| 上报令牌 | — | 与后端 `QQ_INGEST_TOKEN` 一致 |
| 采集后回执 | 关 | 调试期开，稳定后关 |
| AI 结构化 | 开 | 见下节 |
| AI 结构化超时 | 60 秒 | **单条消息**的模型预算。超时退回规则解析 |
| AI 结构化等待 | 20 秒 | **下限**。实际阈值按模型近期耗时自动放大（最多 120 秒）。宁大勿小，见下节 |
| 指定模型提供商 ID | 空 | 留空用默认模型 |

### 采集哪些身份

`owner` / `admin` / `member`。默认只采前两个。

**注意这跟 AstrBot 自己的管理员名单是两回事。** 插件读的是 OneBot 原始事件里的 `sender.role`（群内身份），不是 `event.is_admin()`（AstrBot 后台管理员）。混用的话，任何 bot 管理员在任意群里发链接都会被收进来。

身份会缓存 10 分钟，避免群里刷屏时逐条查群成员接口。刚被撤掉管理员的人，10 分钟内发的消息仍可能被当成管理员。

### 额外采集指定的人

`capture_senders` 填 QQ 号，**不看群内身份照收**。和上面的身份白名单是**并集**：名单里的人照收，群主/管理员也不受影响——它只做「再加一个人」，不会把采集面缩窄。

两种写法：

| 写法 | 含义 |
|---|---|
| `123456789` | 这个人在所有被监听的群里都收 |
| `987654321:123456789` | 只在这个群收；`@` 分隔也认（`987654321@123456789`） |

**必须填 QQ 号，昵称不算数**：昵称随时改、还能重名，QQ 号唯一且稳定。同一个人在不同群身份不同时，用第二种写法按群收紧。

命中名单的人会直接放行，**省掉一次查群成员接口**——所以给群里那个天天发资源的人配一条，比把他升成管理员更省事，也不动群里的权限结构。

**群白名单永远在前。** 只在 `capture_senders` 写了 `200:123456789`，却没把 `200` 放进 `capture_groups`，那个群一条都不会采——撞上时日志会明确报一次「配了人但这个群没开采集」。这是刻意的：群一开采集，群里**群主/管理员**的分享也会照收，所以不能靠“配了个人”顺手把一个群打开。

**目前没有「只收名单里的人、群主管理员一律不收」的独占模式**：清空 `capture_roles` 不会生效，它会回落到默认的 `owner, admin`（空配置按安全默认处理，这条规则在群白名单上也是同一套）。真要独占，得再加一个开关，别指望把角色那一栏留空。

## AI 结构化

群里常见的排版是「标题写两行 + 片名单独一行 + 提取码隔三行 + 尾巴挂一句广告」，正则只能靠长度和字段名去猜哪行是片名。AstrBot 本来就配了大模型，让它直接读整条消息整理成 `{title, shareUrl, sharePwd}` 更准。

**分工是写死在两边的：**

| 字段 | 谁说了算 | 后端怎么核对 |
|---|---|---|
| `title` | 模型 | 只截断到 120 字；空标题退回正则结果 |
| `shareUrl` | **原文** | 必须在原文里找到同一个 `platform:pwd_id`，对不上整条丢弃 |
| `sharePwd` | **原文** | 必须在原文出现过，否则用正则的码 |

模型把短链补全、把 id 记错一个字符，都会被挡在入库之前。**模型漏掉的链接也不会被补回来**——这是纯 AI 策略的取舍，下面细说。

优先级只有两态，中间没有"两边掺着来"：

1. **AI 给了有效条目 → 只入库 AI 交的这批**。标题、提取码全用 AI 的，正则的标题一条都不掺；AI 没覆盖到的链接**直接丢弃**。
2. **AI 一条都没给对（超时 / 没模型 / 返回空 / 全是编造）→ 整条消息退回正则**，否则这条消息等于白采。

第 1 条是有代价的：模型漏一个链接，这个链接就不入库，正则不会替你补。这里选的是「标题来源统一」，不是「链接收全」。丢了多少后端日志写得很清楚：

```
QQ 采集：纯 AI 策略丢弃 19 条 AI 未覆盖的链接（AI 采纳 10 / 原文共 29）
```

出现这行通常意味着模型没把合集贴读全——先看 `ai_timeout` 是不是偏小，或者换个更听话的模型。

单条消息送模型的上限是 **10000 字 / 100 个资源**。合集贴动辄几十个链接，早期 2000 字 / 10 个的上限会把后半段切掉，纯 AI 策略下那部分等于直接丢。现在这档基本碰不到：真撞上了就是一条消息塞了一百多个分享，属于异常。

### 结算窗口（ai_settle）

结构化是异步的，发送不等它。一条消息进队列后，模型有一段等待时间：

- **在阈值内回话 → 带上 `items` 发** —— 后端按纯 AI 策略核对入库，标题用模型的
- **超过阈值还没回话 → 先发** —— 这条没有 `items`，后端走规则解析

**这是一道硬悬崖，不是软降级。** 后端 `upsert_many` 明确不覆盖已入库的标题（防止资源库被后来的帖子改得越来越标题党），所以一条消息一旦按规则解析入库，模型后来给出的标题就**永久补不回来**了。等不等得到，只在这几秒之间。

它的代价却很小：模型 3 秒回话，这条就 3 秒发走，阈值多大都不影响；阈值只在"模型真的还没回话"时才会花出去。所以**宁大勿小**。

### 阈值会自己长

写死一个数注定踩线——模型耗时是会漂的（换模型、服务商排队、夜里负载）。写死 15 秒，17 秒的模型就**每条都掷硬币**，表现正是"AI 结构化一会可以一会不可以"。

现在插件自己记账：每次真正跑完的调用（**包括迟到返回的**）都记一笔耗时，实际阈值 = `max(ai_settle, 近 20 次最慢的 1.6 倍)`，上限 120 秒。

```
pantrace: AI 迟到 17.2s（本次阈值 20s）返回 9 个资源，这条已按规则解析入库，标题未采用。等待阈值 27s，模型近 1 次中位 17.2s / 最慢 17.2s
```

第一条约 17 秒的消息会踩一次线，但从那以后阈值自动抬到 27 秒，同样的模型不会再踩第二次。报错和超时**不**计入样本——模型出故障时最不能做的就是反过来把阈值压低。

`ai_settle` 因此退化成"下限"：想让首条也尽量等到，把它填成你模型的最慢耗时；不在意首条踩线就留默认。

### 先确认它到底在用哪个模型

插件加载完就自报一行，不用等群里来消息：

```
pantrace: AI 结构化使用模型 kimi-k2-0905-preview（未指定 ID，用 AstrBot 当前默认模型）
pantrace: AI 结构化使用模型 deepseek-chat-v3（提供商 ID：deepseek-main）
```

模型名是按 AstrBot 的 Provider 对象现取的（`get_model()` / `provider_config.model` / `meta().model` 逐级兜底），所以 WebUI 里改了模型，重载插件就会看到新名字。**只在模型变化时打一次**，不会每条消息刷一行。

之后每条汇总日志也带上模型，出问题不用翻配置：

```
pantrace: 采集 1 条消息（AI 命中 1 条 / 提交 29 个，模型 kimi-k2-0905-preview 中位 2.4s）→ 入库 19 条，新增 19 / 更新 0，队列剩余 0
```

取不到名字时这行不会出现，AI 链路照跑——名字只是日志，不参与任何判断。想确认"是不是我配的那个"，看重载后这一行最快。

### 日志里同时给出提交数和入库数

```
pantrace: 采集 1 条消息（AI 命中 1 条 / 提交 29 个，模型 kimi-k2-0905-preview 中位 2.4s）→ 入库 19 条，新增 19 / 更新 0，队列剩余 0
```

`AI 命中` 是模型成功结构化的消息条数，`提交` 是模型给出的资源个数。提交多于入库有两个原因：模型把同一链接写了两遍（后端折叠），或者链接在原文里找不到（后端判编造）。明细看后端那行 `QQ 采集：AI 条目被拒 N 条`。

### AI 为什么没生效，日志会直说

以前只会剩一句「AI 结构化 0 条」，看不出来是没配模型还是模型超时。现在会给原因（同类原因 5 分钟内只报一次）：

```
pantrace: AI 结构化没起作用 —— 没取到大模型。去 WebUI「模型提供商」启用一个，或在插件里填「指定模型提供商 ID」×1
pantrace: AI 结构化没起作用（模型 kimi-k2-0905-preview，等待阈值 20s，近 12 次中位 4.2s / 最慢 35.1s）—— 模型还没回话就到了等待阈值，本条先按规则解析入库了×2
```

它会把**模型多快**和**现在等多久**一起打出来，两个数一比就知道该不该换模型：中位 4 秒最慢 35 秒，说明模型抖得厉害；中位 15 秒以上，就该在「指定模型提供商 ID」里换一个不用思考档的。

常见的几条：`没取到大模型`（没配/没启用模型）、`模型还没回话就到了等待阈值`（模型慢，阈值会自动放大，长期如此就换模型）、`模型返回了空文本`（拒答/被截断）、`模型认为原文没有网盘链接`（多半是卡片内容没挖到）。

不想花额度就把「AI 结构化」关掉，完全走正则；关掉之后不会再报这类提示。

结构化跑在独立任务里，不在消息处理函数里——模型动辄几秒，放 handler 里会把群消息处理和其他插件一起拖慢。并发上限 3，同时在途的消息最多 12 条，超出的直接走正则，链接照样入库。

## 规则解析（AI 关闭或失败时）

插件只上报原文，标题由后端解析。规则覆盖群里常见的写法：

| 情况 | 结果 |
|---|---|
| 空行分段 | 上一段的标题不会配给下一段的链接 |
| 片名独占一行 | 配给同段后续的链接 |
| 链接行自带标题 | 优先用自带的（`三体 第一季 https://…`） |
| 链接行只写平台名 | 不算标题，用上一行（`夸克 https://…`） |
| 元信息行 | 直接出局（`导演：辛爽`、`年份：2023`） |
| 提取码 | 就近分配，一码只配一链 |

## 卡片消息

QQ 里转发的网盘分享多数是**卡片消息**，`message_str` 里只有一句「[卡片消息]」甚至空白，标题和链接都在 json 段里（`meta.news.title` 和 `jumpUrl`）。插件会挖这一层，否则群里最标准的分享方式反而一条都采不到。

卡片里同时有头像 CDN、封面图、跳转统计链，只保留网盘域名的那些。

## NapCat 侧的必要条件

- 群消息能正常上报（AstrBot 日志里看得见群消息）
- 机器人账号在目标群里，且**没有被禁言**——禁言期间收不到消息
- 群消息类型配置里包含**群聊普通消息**，不是只收 @ 机器人

## 验证

让群主在目标群发一条带广告尾巴的分享，看三个地方：

**一、AstrBot 日志**

```
pantrace: 采集 1 条消息（AI 命中 1 条 / 提交 1 个，模型中位 1.8s）→ 入库 1 条，新增 1 / 更新 0，队列剩余 0
```

**二、后端日志**

```
QQ 采集：1 条消息 → 1 条链接，新增 1 / 更新 0
```

**三、站点** 搜片名，或者打开「今日更新」（只列 QQ 群采集进来的资源）。

### 排查

| 现象 | 先查 |
|---|---|
| 一条都没采 | 群号填了没有、总开关开了没有 |
| 群号对了还是不采 | 发消息的人是不是群主/管理员；机器人是否被禁言 |
| 采到但标题很糙 | 看那行「AI 结构化没起作用」，它会说明是没模型、超时还是返回非 JSON |
| 日志停了一段，之后一批涌进来 | 后端抖过或重启过。看有没有 `连续 N 次上报失败` 和 `队列已满` 两行 |
| 日志里没有 `pantrace` | 插件没加载成功，看 WebUI 插件页的报错 |
| 重载插件卡十几秒 | 正常上限 2+15 秒：正在把队列里剩下的发完。后端不可达时不会跑退避 |

## 已知限制

- **合并转发的聊天记录**（Forward 段）里的链接拿不到。需要在协议层展开，当前不处理。
- **队列只在内存里。** 极端情况（AstrBot 进程被 kill）会丢未发出去的几条；正常重载会先排空再退出。
- 一个卡片通常只带一个网盘链接。
- 群名不采集（要额外查一次接口，收益不值），落库后「来源」列显示的是 `QQ群<群号>`。
- 采集进来的资源 `origin=qq`、`source_level=1`，搜索排序比上游爬取的靠前。

## 和后端的关系

```
NapCat → 本插件（判定 + 结构化）→ POST /api/ingest/qq → qq_intake.py（校验）→ store.ingest()
```

后端需要在 `.env` 里配：

```ini
QQ_INGEST_ENABLED=true
QQ_INGEST_TOKEN=<和插件里填的一致>
```

令牌要单独设，别复用 `ADMIN_TOKEN`：AstrBot 可能跑在另一台机器上，不该让它拿着能改后台配置的口令。
