# 本地库（80 万条）与 tg / haisou 的分工方案

> 写于 2026-11-21。事实基础：`backend/data/library.db` 本地样本 30303 条（2026-11-20 文档订阅导入），
> 代码现状为 `store.search()` 已实现但**未接入 `/api/search`**，本地库目前只写不读。
> 线上 80 万条的结构与此一致，差异只在量级与导入批次，**启用前必须用本文第 5 节的 SQL 复核一遍**。

---

## 0. 结论先行

1. **本地库不做第三个"通道"，做并行补充层。** 前端仍只有「实时 / 全网」两档，用户心智不变。
2. **本地库的首要价值是兜底，不是主力。** 80 万条是文档订阅导进来的冷数据，没有行为信号、没有新鲜度优势。让它抢一手源的位次，用户会看到一堆"搜得到、点开已失效"，这比没结果更伤。
3. **不体检就启用，等于把一批没验过货的链接直接推给用户。** 启用前必须先跑一遍存活率抽检，按结果分档决定策略（见第 5 节）。
4. **一句话分工**：tg/haisou 负责"今天有什么"，本地库负责"以前有过什么、现在还开得了吗"。前者是入口，后者是地板——地板不能当地板砖用。

---

## 1. 为什么是这个定位

### 1.1 数据事实（本地样本实测）

| 指标 | 实测值 | 含义 |
|---|---|---|
| 总量 | 30303 | 线上约 80 万 |
| `check_state` | 100% `unknown` | **从未探活**，不知道多少是死链 |
| `hit_count` / `click_count` | 100% 为 0 | 没有任何行为信号，热度排序完全失效 |
| `file_count` / `size_bytes` | 100% 为 0 | 文档表里没有这两列，卡片上这两个信息位永远是空的 |
| 平台分布 | quark 16777 / xunlei 13526 | **只有两个盘**，用户选百度/阿里时库里没有货 |
| 来源 | 100% `doc:*` | 全部来自内部收集表订阅，不是搜索回填 |
| 同名标题 | 3927 组 | 去重必须按身份，不能按标题 |

这些数字决定了三件事：

- **库里排序不能靠 hit/click**（全是 0），只能靠 FTS bm25 + `source_level` + 新鲜度。`_score()` 现有权重里，命中/点击那两项（120 / 200）对这批数据完全不起作用。
- **平台偏科是硬伤**。补位有天花板：用户要百度，库里一条都补不出来。这不能靠代码解决，只能靠继续扩文档订阅的源。
- **探活是前置条件，不是优化项**。`HIDDEN_STATES` 只隐藏 `bad`，但库里一条 `bad` 都没有——因为一条都没检过。

### 1.2 为什么不把库做成插件

整个搜索架构是插件化的，第一反应肯定是"再加一个 library 插件"。**不要这么做**，四个理由：

| 问题 | 后果 |
|---|---|
| 健康统计污染 | `liveness` 会把本地库记成永远健康的源，拉高整体健康率，掩盖真实上游的问题 |
| `_pick_plugins` 分流失效 | 库要么伪装成 `plugin`（那 `src=plugin` 时被强行带上，等于偷偷合并），要么新增 `source_kind`，等于把通道从两档改成三档 |
| BasePlugin 的开销全是白付的 | 4~6 秒窗口、`complete` 语义缓存、失败分类、工作池——对一次 50ms 的本地 SQLite 查询毫无意义 |
| 同步阻塞 | `store.search()` 是同步 SQLite，塞进 async 插件里必须 `to_thread`，绕一圈还是回到"单独一层" |

**结论：新建 `backend/app/search/library.py` 作为独立一层，在 `_run_search()` 里与 `engine.search()` 并行调用。** 它不进插件注册表，不进 `liveness`，不进 `/api/health` 的 `sources`。

## 2. 三层结构

| 层 | 角色 | 何时出手 | 边际成本 |
|---|---|---|---|
| **L1 实时源**<br>tg / haisou | 采购：发现今天的新资源 | 每次搜索必跑 | 有（haisou 计费 / tg 有耗时） |
| **L2 本地库**<br>80 万条索引 | 库存：兜底、补位、续页 | 按 R2 的四个触发条件 | 0 |
| **L3 探活**<br>check.py 状态机 | 验货：保证"点得开" | 后台异步 | 0（匿名接口） |

零售类比：先看采购能不能满足需求，不能满足才动库存；动库存之前必须掂一下保质期。

## 3. 四条关系规则

### R1 · 身份去重：同一资源只出现一次

- 身份 = `platform:pwd_id`（`sdk/urls.py` 的 `ParsedShare`），**不是 URL 字符串**。同一个分享在不同渠道有不同短链和参数，按 URL 去重等于没去重。
- 上游条目解析出 `pwd_id` 后与库比对：命中就**丢弃库条目**，把库侧的历史信息（`resourceId`、`checkState`、`hitCount`）贴到上游条目上。这是增强，不是重复。
- **必须踩住的一个坑**：`SearchResult.result_key()` 在 `unique_id` 为空时会退化成 `title_{title}_{channel}`，而库里同名标题有 3927 组。库条目若直接混进 `merge_search_results`，**不同资源会被当成同一条吞掉**。库条目必须带 `unique_id = f"lib-{resourceId}"`，或者干脆走独立的合并函数（推荐后者，见第 4 节）。
- 解析失败时（短链、天翼/微云这类），降级为 `(platform, 规范化标题)` 比对；仍失败就**放行不合并**——宁可重复一条，不可误吞一条。

### R2 · 兜底优先于补位

四个触发条件，按优先级执行：

| 优先级 | 条件 | 库的动作 | 响应标记 |
|---|---|---|---|
| 1 | 上游全挂（本会返回 504） | **全量接管** | `degraded: "library"` |
| 2 | 上游零结果 | **接管** | `degraded: "library"` |
| 3 | 用户选的平台上游没覆盖（选了百度只回夸克） | **补该平台** | `library.mode: "supplement"` |
| 4 | 上游正常 | **补位**，排在实时结果之后 | `library.mode: "supplement"` |

优先级 1 是这套方案最大的即时收益：**504 变 200**。上游签名过期、限流、超时的时候，站不再是"挂了"，而是"降级但可用"。

### R3 · 补位有深度上限

- 补位最多到**第 3 页（60 条）**，单次最多补 20 条。
- 理由：库是冷数据，越往深翻死链密度越高。翻到第 10 页全是三年前的失效链接，用户对整站的判断就定型了。
- **库独立入口（`src=library`）不受此限**，那是用户明确要看库存。
- 补位进来的条目必须在 UI 上和实时结果有可见区分，不能混成一片。

### R4 · 零成本不等于零风险

- 库条目一旦被展示，**必须进探活队列**（复用 `check.schedule`，TTL 6 小时）。展示不验货，等于把死链直接递到用户手里。
- `check_state = bad` 的不出库（`HIDDEN_STATES` 已实现）。
- `uncertain` 可以出库，但卡片要标"未核验"——判不准就说判不准，这是 `check.py` 原本的纪律。
- 兜底模式下**允许放宽**：上游全挂时，宁可给一条 `uncertain` 的，也好过给空白页。

## 4. 落点：改哪几个文件

| 文件 | 改什么 | 风险 |
|---|---|---|
| `search/library.py`（新） | 库检索层：调 `store.search()`、身份比对、深度截断、形状转换、降级判断 | 新增，隔离 |
| `store.py` | `_to_item()` 补 `pwdId` 内部字段；`search()` 加 `exclude_keys` 参数（身份黑名单，避免取回来再丢） | 低，向后兼容 |
| `main.py: _run_search()` | `asyncio.gather(engine.search, library.search, return_exceptions=True)`；库异常只记日志，不拖垮主链路 | 中，需保证库失败时行为与今天完全一致 |
| `main.py: _export_search()` | 合并点在 `_apply_hidden` **之后**、`_public_body` **之前**（`_public_body` 会把 shareUrl 换成 `/go/<token>`） | 低 |
| `main.py: /api/search` | 新增 `src=library` 第三档 | 低 |
| `engine.py` | **不动**。库不走插件，不污染 source 统计 | — |
| `frontend/src/App.vue` | 结果面板加一行"另有 N 条来自本地索引"；兜底时加一行灰字"实时源暂不可用，以下为本地索引结果" | 低 |

响应字段扩展（全部新增，不改动现有字段，老调用方无感）：

```jsonc
{
  "items": [...],
  "library": {
    "used": true,
    "mode": "supplement",   // supplement | fallback | off
    "added": 12,            // 本次从库里补了多少条
    "deduped": 37,          // 与上游重复、被合并掉多少条
    "truncated": false      // 是否因深度上限截断
  },
  "degraded": "library"     // 仅兜底时出现
}
```

**缓存的两个细节**：

1. 库补位后的结果会进现有 `_cache`（TTL 5 分钟），窗口内库的新增看不到——可接受，不为它单独开缓存。
2. **降级结果的 TTL 要短**（建议 60 秒）。否则上游恢复了，用户还要看 5 分钟的降级结果，会以为站一直没恢复。

## 5. 启用前必做：数据体检（第 0 步）

在动任何代码之前，先回答一个问题：**80 万条里有多少还活着？**

### 5.1 结构体检（只读，1 分钟）

```sql
-- 状态与平台分布
SELECT check_state, COUNT(*) FROM resources GROUP BY 1 ORDER BY 2 DESC;
SELECT platform, COUNT(*) FROM resources GROUP BY 1 ORDER BY 2 DESC LIMIT 15;

-- 冷热与完整度
SELECT SUM(hit_count > 0), SUM(click_count > 0), SUM(file_count > 0), SUM(size_bytes > 0)
FROM resources;

-- 新鲜度（按首次入库时间分年）
SELECT strftime('%Y-%m', first_seen_at, 'unixepoch') m, COUNT(*)
FROM resources GROUP BY m ORDER BY m DESC;

-- 标题重复（决定去重策略的容错度）
SELECT COUNT(*) FROM (SELECT title FROM resources GROUP BY title HAVING COUNT(*) > 1);
```

### 5.2 存活抽检（半天）

```sql
-- 分层抽样：每个平台随机取 500 条，共约 5000 条
SELECT id, platform, url, pwd FROM resources
WHERE platform = ? ORDER BY RANDOM() LIMIT 500;
```

用 `check.py` 的匿名检测接口跑这批样本（**不要用转存账号**，账号是稀缺资源），得到 ok / bad / locked / uncertain 的实际比例。

### 5.3 按体检结果分档启用

| 抽检 ok 率 | 策略 | 说明 |
|---|---|---|
| **≥ 70%** | 全量启用：兜底 + 补位 + 独立入口 | 库里是硬货，可以当第二梯队用 |
| **40% ~ 70%** | 只兜底 + 补位限 1 页（20 条），且**只出 `ok` 条目** | 补位保守，避免死链拖累体验 |
| **< 40%** | **暂停启用**，先清库：全量探活 → 只留 `ok`，其余归档（`archived_at` 置位，不删） | 直接启用是自毁 |

> 我的预判：文档订阅来的链接，出处表格本身不维护，ok 率大概率落在 40%~60%。
> 如果实际低于 40%，方案要退回到"先清库再启用"，别硬上。

## 6. 上线四步（每步有判据、有回滚）

### 第 1 步 · 影子期（3 天，零风险）

库检索并行跑，**结果不返回**，只写日志和计数。

- 观测：每次搜索库会补多少条、多少条与上游重复、库命中率、补位后翻页深度
- 判据：3 天后拿到真实的"补位率 / 重复率"分布，用来定 R3 的深度上限
- 回滚：关一个开关（`LIBRARY_READ=0`）

### 第 2 步 · 兜底期（立刻见效）

只在上游失败 / 零结果时用库。

- 价值：504 → 200；长尾词从"没有这个资源"变成"有结果"
- 判据：兜底请求占比（预期 3%~8%）、兜底结果的点击率
- 回滚：`LIBRARY_FALLBACK=0`

### 第 3 步 · 补位期

正常搜索也补，排在实时结果之后，最多 20 条、最深 3 页。

- 判据：补位条目的点击率 ÷ 上游条目点击率。**低于 1/3 就退回第 2 步**，只保留兜底
- 这一条是硬指标，别用"感觉还行"判断

### 第 4 步 · 独立入口

加 `src=library`，前端先藏在空结果页的"没找到？搜一下本地索引"，观察使用量再决定是否提升为常驻第三档。

- 顺带解锁 P2 的榜单页 / 详情页——库里有 `resourceId`，详情页有东西可展示

## 7. 观测（缺了这套就是盲飞）

每次搜索要能回答"这次结果是谁给的"。建议在 `analytics` 里加三个维度：

| 指标 | 用途 | 报警线 |
|---|---|---|
| 库补位率（补了条的请求 / 总请求） | 判断库是否在起作用 | 持续 0 = 库没接上 |
| 库兜底率（降级请求 / 总请求） | 上游健康度的侧面指标 | > 15% = 上游出事了 |
| 补位条目点击率 vs 上游条目点击率 | 决定第 3 步是否保留 | < 1/3 退档 |

另外 `/api/health` 的 `library` 字段已有 `total` / `by_state` / `by_platform` / `new_today`，
补位上线后建议再加 `read_used_7d`（7 天内被展示过多少条），否则 80 万条里哪些真有用，永远不知道。

## 8. 两件要你拍板的事

**① 默认档要不要挂库？**

我建议挂，但只到第 3 步（补位）。不挂的话，这 80 万条永远只是后台的一个数字，投入的采集和维护成本一分钱收不回来。

**② 兜底时要不要明说"这是降级结果"？**

我建议明说，一行灰字就够。不明说的话，用户以为这是实时结果，点开死链后骂的是整站；明说了，他会理解"现在源有问题，但有结果总比没有强"。**诚实比体面值钱。**

## 9. 与既有规划的衔接

- 这份方案只解决"库怎么用"，不解决"库怎么长"。数据层面最大的短板是**平台偏科**（只有 quark / xunlei），扩文档订阅源要和代码启用同步推。
- 记忆里 P2 的榜单页 / 详情页依赖本地库，本方案第 4 步之后才有意义——库里没被读过的数据，做榜单是空榜。
- `store.py` 是唯一数据入口这条纪律不变；本方案只在 `_to_item()` 加一个内部字段，不新增查询通道。
