# 盘迹 PanTrace · QQ 机器人卡片方案

_2026-11-24 · 老编_

---

## 一、先给结论

**能搬，而且卡片是这个项目最适合的形态——但真正的门槛不在代码，在平台侧的两个数字。**

1. **卡片本身不难**，`msg_type=2` 的 Markdown + `keyboard` 按钮，QQ 官方 API v2 原生支持。难的是**权限**：群机器人要拿到 Markdown 和自定义按钮能力，得先上架、近 7 天平均用到 3 个群、每月 15–20 号才统一审核一次。这不是技术问题，是等。
2. **额度比权限更致命**：一个用户 @ 一次机器人，只换来 **1 个 `msg_id` 和 5 次回复**（机器人是群主/管理员时 50 次）。翻一页消耗一次，翻四页就哑了。方案里所有交互设计都是围着这个 5 转的。
3. **我们有一个别人抄不走的优势**：`/go/<token>` 这套点击转存机制。卡片正文里**一个网盘域名都不出现**，按钮指向我们自己的域名，落地页当场转存。这一条同时解决了 QQ 的链接风控、链接外露、以及"用户拿去转卖"三件事。搜盘站搬到 QQ 死掉的原因基本都是直接甩 `pan.quark.cn` 链接，我们不用走那条路。

一句话：**代码两三天，权限看命，交互设计把 5 次额度用到极限。**

## 二、现状（改之前先认清楚）

`astrbot-plugin-pantrace` 已经存在，但它**只做采集，不搜索**，README 里写得很明确：

> **不做搜索。** 这是刻意的：搜索是用户主动发命令，采集是后台静默跑，两者对事件的处理方式、出错后的表现、日志噪声完全不同，混在一个插件里排查问题会互相干扰。

这个判断我认同，方案不推翻它。**采集插件一行不动，另起一个搜索插件。**

同时有一条架构事实必须点明，它决定卡片能做到什么程度：

| | NapCat（aiocqhttp） | QQ 官方机器人（qq_official） |
|---|---|---|
| 读发送者群身份 `sender.role` | ✅ 有 | ❌ 官方 API 不返回 |
| 发 Markdown | ⚠️ 依赖协议端版本，不稳定 | ✅ 原生 `msg_type=2` |
| 发 keyboard 按钮 | ❌ 官方协议无此消息段，社区做法是 `send_packet` 自己组 protobuf（灰色手段） | ✅ 原生支持，5 行 × 5 个 |
| 进群门槛 | 扫码即用 | 需上架审核 |

**所以分工是确定的：**

```
NapCat 号（自建）  ── 采集群分享 ──► /api/ingest/qq ──► 库
官方机器人（上架） ── 搜索 / 卡片 ──► /api/bot/search ──► 库 + 上游
                              └── 同一个后端、同一个库
```

采集必须留在 NapCat（要读群身份，官方 API 给不了）；要真卡片只能走官方机器人。两个号并存，一个负责喂库，一个负责用库。

> 如果你的机器人**还没上架**，看第六节的 P1——纯文本版不依赖任何权限，可以先跑起来，卡片等权限。

## 四、最值钱的一个设计：默认查库，不查全网

这是整个方案里唯一需要你拍板的产品判断。

**网站上的默认是 `src=tg`（实时上游）**，因为网页用户能等 5 秒，而且是一次性访问。**群聊里必须反过来，默认 `src=library`。**

三个理由：

1. **延迟**。库里 FTS5 查询是毫秒级，`/go` 之外整条链路 200ms 内出结果；全网要 3–10 秒。群里等 8 秒，用户已经去别处问了，而且下一个人还会再问一遍。
2. **成本**。全网每查一次都真烧上游额度。群是高频场景——20 个群一天几百次搜索，额度撑不过一周。库的边际成本是 0。
3. **质量**。库里进过的都过了 `_apply_hidden`（多人举报剔除）和链接探活，标题是清洗过的；全网回来的标题带广告、带公众号导流、带死链。

代价是**覆盖率**。所以空结果卡必须给一个明确的按钮：

```
本地库没有「赛博朋克 边缘行者 4K」
> 库里收录了 41 万条，但没这一条

[去全网搜（约 10 秒）]  [记下来，我去找]  [去网站搜]
```

**把成本交给用户主动选择**。他愿意等 10 秒就付这个额度，不愿意就转网站——顺带完成一次回流。这一条同时解决了成本、延迟和引流，是我最想推的设计。

命中阈值建议：库返回 < 3 条时，卡片顶部加一行"库里只有 2 条，要不要去全网补？"，而不是自动降级。项目里"不做自动降级"的约定要守住——用户得知道这次查的是什么。

## 五、卡片设计与额度账本

### 5.1 五张卡

**搜索卡**（正文列 5 条，按钮两行半）

```
# 盘迹 · 三体
> 本地库命中 6 条 · 来自 3 个群与 2 个 TG 频道

**① 三体 全集 4K 修复版**
夸克网盘 · 18.7 GB · 可访问

**② 三体 三部曲 有声书 全**
百度网盘 · 3.2 GB · 需提取码

**③ 三体 电视剧 全 30 集**
阿里云盘 · 42.1 GB · 可访问
---
点按钮直接打开；落地页自动转存，链接 30 分钟内有效
```

按钮布局（`rows` 最多 5 行、每行最多 5 个）：

| 行 | 按钮 | `action.type` |
|---|---|---|
| 1 | ① 夸克 ② 百度 ③ 阿里 ④ 迅雷 ⑤ 微云 | `0` 跳 `/go/<token>` |
| 2 | 换一批 / 只看夸克 / 今日群分享 | `2` 指令，或 `1` 回调 |
| 3 | 本地库没有？去全网搜 / 报失效 / 求资源 | `2` 指令 |

第一行是关键：**每条结果一个按钮，label 只放序号 + 平台简称**。正文里也用 ① 编号对应。手机 QQ 上正文里的 `[文字](url)` 链接会被折叠成"查看链接"，按钮才是真入口。

**空结果卡 / 今日卡 / 求资源卡**：见第一节的示意图和第三节的映射表。

### 5.2 额度账本：5 次怎么花

| 动作 | 消耗 | 累计 |
|---|---|---|
| 用户 `@盘迹 三体` | 生成新 `msg_id`，额度 5 | 5 |
| 回结果卡（`msg_seq=1`） | −1 | 4 |
| （可选）超过 8 秒补一句"还在找"（`msg_seq=2`） | −1 | 3 |
| 用户点「下一页」 | **指令按钮 → 输入框填入 `@盘迹 三体 2` → 用户发送 → 新 msg_id** | **重置为 5** |

**这就是为什么翻页必须用指令按钮（`action.type=2`），不能用回调按钮（`type=1`）：**

- 回调按钮每点一次吃一次额度，4 次以后没额度了，用户点按钮没反应。
- 回调要维护「这个 msg_id 对应哪个查询」的会话映射。机器人一重启、或者跑两个实例，上下文就断。指令按钮**完全无状态**——查询参数在消息文本里，重启随便重。

代价是用户要再按一次发送。这个交换在群聊场景里是划算的。

`msg_seq` 必须逐次递增。同一个 `msg_id` + 同一个 `msg_seq` 重复发送会直接报错——这是最容易踩的一个坑，AstrBot 的官方适配器是否代管要看版本，插件里自己维护最保险。

### 5.3 不下发的字段

机器人侧只取 `title / platform / platformName / sizeBytes / fileCount / checkState / shareUrl`。

- `shareCode`（网盘分享 id）永远不下发，`_public_body` 已经清了，别在 bot 通道里又加回来。
- `sharePwd` 只有在**不能转存**的平台（天翼/微云/光鸭这些没有 adapter 的）才有值——那种情况卡片上必须显示，否则用户拿到一条要密码却没有密码的链接。这个判断 `_can_mirror` 已经做了，直接用。

## 六、后端改动

### 6.1 新增 `POST /api/bot/search`

不能直接让机器人打 `/api/search`，三个原因：

1. **票据绑 IP**。`guard.verify(ticket, ip)` 按来源 IP 签票，机器人所有群共用一个出口 IP，领一次票能过；但——
2. **限流是按 IP 的**。`RATE_LIMIT_PER_MINUTE` 默认 30，一台机器人服务几百个群共用一个 IP，20 个人同时搜就 429 了。
3. **返回的是相对路径** `/go/xxx`。机器人拼不出绝对地址（可以让插件自己拼 `base_url + shareUrl`，但更该由后端统一给）。

接口形态：

```
POST /api/bot/search
Header: x-bot-token: <BOT_TOKEN>
Body: { "q": "三体", "platforms": ["quark"], "page": 1, "src": "library",
        "openid": "<member_openid>", "group": "<group_openid>" }
```

返回 `{ code, items[], pagination, tookMs, hint }`，`shareUrl` 是**绝对地址**。

限流三道，缺一不可：

- 按 `group:member` 的 openid 限流（建议 8 次/分钟）——挡单人在群里刷
- 按 `bot_token` 全局限流（建议 120 次/分钟）——挡机器人整体过载
- `src=tg` 时 cost 乘 2（和 `/api/search` 的 `refresh` 一个道理）

### 6.2 要重构的一段（有风险，单独回归）

`main.py` 的 `search()` 从 861 行到 1058 行，把「限流 → 票据 → 缓存 → 单飞 → 埋点 → `_export_search`」串在一起。bot 通道要复用**缓存和单飞**（否则 20 个群同时搜同一个词会把上游打穿），但不该复用票据。

做法：把从 `query = q.strip()` 到 `return _export_search(...)` 抽成 `_search_core(...)`，`/api/search` 和 `/api/bot/search` 各自做完自己的鉴权限流后调它。

**回归时必须验的是 `_export_search` 的调用顺序**：`_apply_hidden` → `check.annotate` → `_public_body`。这三步顺序一动，链接就会以明文形式漏进缓存。这是全站唯一一处"错了不会报错、只会悄悄漏"的地方。

### 6.3 其它

- `config.py` 加：`BOT_TOKEN`、`PUBLIC_BASE_URL`、`BOT_DEFAULT_SRC`（默认 `library`）、`BOT_RATE_PER_MIN`。
- `/api/feedback` 支持 `x-bot-token`：验过就跳过按 IP 的限流，改按 `visitor`（openid）限流。否则全群共用一个 IP，一个人提交频繁会把整群堵死。
- `/api/today`、`/api/group`、`/api/platforms` 本来就是公开 GET，直接用，不改。
- 采集侧 `/api/ingest/qq` 一行不动。

## 七、插件设计

新建 `astrbot_plugin_pantrace_search`，和采集插件并存，互不 import：

```
astrbot_plugin_pantrace_search/
  main.py          # 命令解析、事件过滤、限流、日志
  commands.py      # 文本 → 结构化意图（关键词 / 页码 / 平台 / 全网 / 今日 / 求）
  render.py        # 两种渲染器：markdown 卡片 / 纯文本兜底
  keyboards.py     # 按钮布局，产出 keyboard JSON
  client.py        # HTTP，带 x-bot-token，超时与重试一次
  _conf_schema.json
```

三个设计约束：

1. **渲染器可切换**。`render_mode: card | text | auto`。`auto` 时先试 markdown，发送失败（权限没开/接口报错）自动降级到 text 并记一条 WARNING——只在第一次报，别刷屏。这是权限没批下来时不至于瘫痪的保险。
2. **命令解析要短且可预测**。`@盘迹 <关键词> [#平台] [页码]`，不搞子命令树。`今日`、`求 xxx`、`群`、`帮助` 是三个固定词，命中即走专用分支。
3. **绝不拦截普通消息**。只处理 `@机器人` 的事件。采集插件已经全量监听群消息了，搜索插件再加一层过滤会让排障变成猜谜。

## 八、必须预先知道的坑

按踩到的概率排序。

1. **自定义按钮 `keyboard.content.rows` 是"内邀开通"**。没开通时只能传 `keyboard.id`（平台预设模板，还要单独申请）。这是整个方案最大的不确定性——**P1 纯文本版必须先跑起来**，卡片是增量，不是前提。
2. **Markdown 权限的申请条件**：群机器人已上架 + 近 7 天平均使用群数 ≥ 3 + 场景合理，每月 15–20 号统一审。群数不够就是不够，没有加速通道。
3. **传了 `markdown` 之后 `content` 和 `ark` 必须为空**，否则接口报错。参数互斥。
4. **同一 `msg_id` + 同一 `msg_seq` 重复发送会失败**。递增，或者用 `msg_id` 换 `event_id`。
5. **被动窗口 60 分钟、每消息 5 次回复**。机器人是群主/管理员时放宽到 50 次。单聊 C2C 更紧（60 分钟 4 次）。所以重度用户该被引导去网站。
6. **链接要报备**。管理端「开发设置 → 消息 URL 配置」，把自己的域名加进去。没报备的链接在 ark 里可能被拦。
7. **QQ 内置浏览器**。落地页 `location.replace(j.url)` 跳的是 https 的网盘分享页，能开；但如果哪天改成 `quark://` scheme，QQ WebView 大概率静默失败。落地页保持 https，并把「复制链接」按钮放显眼位置。
8. **标题敏感词会被消息审核拦整条**。上游标题里什么都有。出口必须过一道关键词过滤，命中的直接不回（而不是回一条半残的卡）。建议在 `_public_body` 之后加一个 `_card_safe(items)`，只作用于 bot 通道，不动网站。
9. **没有 `msg_id` 就不能往群里发东西**。群里主动推送受 qpm 和每群每天 1000 条的额度限制。「今日更新」只能用户主动问，不能定时推——除非机器人做了认证，那时可以单独设计一个早报。
10. **同群多人同时搜同一个词**。库查询本身没问题，但 `src=tg` 会撞上游限流。bot 通道复用单飞锁，别绕过。
11. **只给前 5 条配按钮**。第 6 条以后怎么办？两个选择：一是「⑤ 更多」跳网站搜索页；二是把 6–10 条也列进正文（无按钮），靠正文链接点。前者更干净。
12. **NapCat 发按钮要自组 protobuf**（社区 `astrbot_plugin_button` 那套 `send_packet` + `MessageSvc.PbSendMsg`）。能用，但随 QQ 版本更新失效是迟早的，且有账号风险。**我不建议把它当正式方案**，只适合你自己内测看效果。
13. **卡片的视觉效果上限不高**。QQ markdown 不支持表格、不支持自定义颜色、不支持卡片封面。想要网站的深色质感，只能发图片（`msg_type=7` 富媒体）——但图片不可点、不可复制链接。折中做法：搜索走卡片，**「今日更新」可以做成一张图**（浏览场景不需要点击）。

## 九、分阶段落地

| 阶段 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| **P0** | 后端 `POST /api/bot/search` + `_search_core` 抽取 + feedback 放宽 | 无 | `curl` 带 token 能查到库结果，`shareUrl` 是绝对地址；超频返回 429；不带 token 返回 401 |
| **P1** | 插件骨架 + 纯文本渲染 + 命令解析 | P0 | 群里 `@机器人 三体` 返回最多 5 条，序号可点；`今日`、`求`、`群` 各自走通 |
| **P2** | markdown 卡片 + 按钮 + `auto` 降级 | P1 + **权限** | 卡片正常渲染；关掉权限后自动降级不报错 |
| **P3** | 报失效、换筛选、翻页按钮 | P2 | 报失效后该条在下次搜索结果里消失（走 `_apply_hidden`） |
| **P4** | 主动推送早报（需机器人认证） | 认证 | 每群每天一条，带退订 |

P0 和 P1 是**不依赖任何平台权限**的，今天就能开工。P2 的两天活其实半天能写完，剩下的时间在等审核。

## 十、我不建议的三条路

1. **不建议用 NapCat 组包发按钮当正式方案**。`send_packet` 那套是逆着协议走的，QQ 一次协议调整就全废，而且账号风险算在你自己的号上。内测看效果可以。
2. **不建议做有状态会话**（回调按钮 + 数据库存"这个 msg 对应哪个查询"）。为了省用户一次回车，换来会话过期、多实例不一致、重启丢上下文三类问题。指令按钮无状态，多花用户半秒，省你三天。
3. **不建议在群里主动推搜索结果或榜单**。额度只是一方面，主要是群里刷屏两天就会被踢。要推就推「今日群分享」一条，且默认关。

## 十一、开工前需要你确认的两件事

1. **机器人现在跑在哪个协议端？** 如果只有 NapCat，那 P2 之前先按纯文本设计，卡片要等官方号上架。如果官方号已经在审核或已上架，直接排 P2。
2. **库的默认来源对不对？** 我在方案里定的是 `src=library`（毫秒级、零成本），全网要用户显式点。如果你觉得群里更应该给实时结果（比如库还很薄），改成 `tg` 也行，但要把限流收紧到 3 次/分钟，否则额度撑不住。
