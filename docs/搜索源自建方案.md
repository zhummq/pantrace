# 自建搜索源方案 · 从 PanSou 与下个吧看两条路

> 读的是 `D:/wangpan/pansou`（Go，113 个插件目录）和 `D:/wangpan/xiageba2`（Nuxt + Prisma）。
> 这份和 `pansou-借鉴清单.md` 互补：那份讲「抄哪个机制」，这份讲「源从哪来、怎么接进现有后端」。
> 结论只对盘迹当前这套 Python + Vue + 单上游 + 转存 SDK 的架构说事。

---

## 0. 结论先行

1. **两个项目不是同一件事**。PanSou 是**实时聚合器**（查的时候去 113 个站现抓）；下个吧是**自建资源库**（资源先入库，查的时候只查自己的库）。我们该学的是后者，不是前者。
2. **「加源」的真正成本不是写代码，是维护**。我实测了 40 个 PanSou 源站，**只有 50% 连得上**；连得上的里面又有一半抓不出东西。写一个插件是半天的事，让它在三个月后还能用，是持续投入。
3. **所以不要做实时多源聚合，做「后台采集入库 + 本地检索」**。用户搜索永远只打本地库，毫秒级返回、零上游依赖；采集失败、源站改版、反爬升级，都只影响「库会不会变新」，不影响「用户能不能搜」。
4. **idatariver 不要删，降级成冷启动补量**。自建库最大的问题是空库没结果，冷启动期需要一条能兜住长尾的通道。
5. **技术选型已验证**：SQLite FTS5 + `1-gram + 2-gram` 预切词，`三体`/`科幻`/`庆余年` 全部召回正常（详见 §5.1）。**别用 `tokenize='trigram'`**，中文两字词会全部搜不到。

## 1. 两个项目到底在做什么

| | PanSou | 下个吧（xiageba2） |
|---|---|---|
| 本质 | 实时聚合搜索 | 自建资源站 |
| 数据在哪 | 别人站上，用时现抓 | 自己库里，Excel 导入 + 后台录入 |
| 查询耗时 | 4 秒窗口，超时转后台补齐 | 几十毫秒（PG 全文索引） |
| 源失效了会怎样 | 那个源的数据直接消失 | 数据还在，只是链接变死链（有校验兜底） |
| 主要成本 | 113 个插件的持续适配 | 采集/录入的人力 |
| 代码量 | Go 约 10 万行（含测试） | TS，业务为主 |

**一句话**：PanSou 把复杂度放在「抓」上，下个吧把复杂度放在「攒」上。我们已经有转存、检活、举报闭环，天然是「攒」的体质。

### 1.1 PanSou 的插件骨架（值不值得抄？值得，但只抄接口）

`plugin/plugin.go:24` 定义 `AsyncSearchPlugin`，每个插件在自己包的 `init()` 里调 `RegisterGlobalPlugin()` 自注册，`main.go` 里 75 个 `_ "pansou/plugin/xxx"` 空导入触发注册。**加一个源 = 加一个包，主流程零改动**——这个设计是对的。

`BaseAsyncPlugin` 替插件挡掉了四件事，插件作者只需要写一个 `searchFunc`：

```
AsyncSearchWithResult(keyword, p.searchImpl, p.MainCacheKey, ext)
                       └── 真正的搜索实现，唯一要写的东西
```

被挡掉的是：请求级状态隔离（`ext` 传参，不写实例字段，避免并发串词）、双层缓存、工作池限流、4 秒窗口 + 后台补齐、失败回退旧缓存。

**这部分值得抄的是「接口形状」，不是实现**。Python 侧不需要 GOB 序列化、分片缓存、自适应并发——那些是 Go 打免费站的性能工程。清单 §4 已经列过不该抄的项，这里不重复。

### 1.2 下个吧的检索实现（真正该抄的部分）

`server/api/source/search.get.ts`，一条 SQL 解决整件事：

1. **jieba 分词 + 别名扩展 + 召回阶梯**（`analyzeQuery`，`server/utils/jieba`）——不是简单 `LIKE %kw%`
2. **`to_tsquery` 而不是 `websearch_to_tsquery`**，注释写得很清楚：后者会静默丢弃括号，`A (B OR C)` 会退化成 `(A & B) | C`
3. **三段式粗筛**：先按 `createdAt` 截断到 2000 条候选（只取 id + 时间，不碰 TOAST 宽列）→ 对这 2000 条算 `ts_rank` 分页 → 最后只回表取 20 行的宽字段。注释给了实测：全量排序再抓 `menu` 列要 8.9 秒
4. **覆盖度打分**：`权重 = 字符数 × 出现次数`，标题精确等于关键词给 3 分、前缀匹配 2 分、包含 1 分
5. **总数单独缓存 Redis 10 分钟**，翻页不重算 COUNT

它的 `Source` 表极简——`title / url / description / menu / searchVector`，没有花哨字段。**资源库不需要复杂模型，需要的是索引和校验。**

## 2. 实测：源站到底能不能用

这是这次调研最有价值的部分，也是在 `pansou-借鉴清单.md` 里没有的。**加源之前必须先跑这一层。**

### 2.1 可达性：40 个域名，只有 20 个连得上

从 113 个插件的源码里提取出全部外部域名，去掉网盘域名和通用库，剩下 40 个资源站，并发探测根路径：

| 结果 | 数量 | 说明 |
|---|---|---|
| 200 | 20 | 能打开 |
| 000 | 16 | DNS 解析失败 / 连接被拒，直接不通 |
| 301/302 | 3 | 跳转，需跟一下 |
| 400/403 | 5 | 反爬或参数问题 |

未通过的典型：`www.91panta.cn`、`www.4khdr.cn`、`squark.cc`、`www.pansearch.me`、`www.yunso.net`、`www.ahhhhfs.com`、`qkpanso.com`、`quark4k.com`、`xiaokupan.com`、`ypfxw.com`。

> **注意口径**：这批数据是在**本机**跑的。本机 `HTTPS_PROXY=http://127.0.0.1:16796`，而项目 `config.py` 的 `use_env_proxy=False`（线上是直连）。curl 默认走代理所以能通，Python 直连就超时——**同一批站，两条网络路径，两种结论**。这份数据只能当「量级参考」，真正加源必须在**部署机**上重跑一遍。

### 2.2 可达 ≠ 可用：五个源，五种死法

挑连得上的逐个验证「能不能真捞出网盘链接」，结果全部失败，而且死法各不相同：

| 源 | 现象 | 死法 |
|---|---|---|
| `www.hjzhencai.top` | 首页 200（0.7s），搜索页也 200，标题正常返回 | **站点转型**：现在是影视站，搜「小红书」0 结果。插件代码没坏，是世界里没有那个东西了 |
| `sdso.top` | 接口 200，返回的不是 JSON | **JS 挑战**：随机 cookie 名 + `btoa` + `location.reload`。PanSou 靠 `goja` 在 Go 里执行 JS 才过，Python 侧得另配引擎 |
| `buerchen.top` | 200，返回 ThinkPHP 错误页 | **接口改版**：`控制器不存在:app\controller\404`，路径没了 |
| `haisou.cc` | 首页 200，API 请求读超时 | **限流/变慢**：我们以前就因「匿名按 IP 每日 100 点」弃用过它 |
| `t.me/s/<channel>` | 全部超时（000） | **网络不可达**：TG 通道必须挂代理，本机/国内直连无解 |

**这五种死法，没有一种能靠「写对代码」避免。** 这是选「实时聚合」还是「采集入库」的决定性依据：实时链路上任何一源这样死，用户当场拿不到结果；采集链路上它只是「今天没补货」。

### 2.3 我们在 Python 侧缺什么

`backend/requirements.txt` 只有 `fastapi / uvicorn / requests / pydantic-settings / cryptography`。抓取链路上缺三样：

| 缺什么 | 什么时候才需要 |
|---|---|
| HTML 解析（`lxml` / `selectolax`） | 源只给 HTML 不给 JSON。**能选 JSON 接口就别选 HTML** |
| `cloudscraper` | 目标站是 Cloudflare 5 秒盾 |
| JS 引擎（`mini-racer` / Playwright） | 目标站是 JS 挑战（如 `sdso.top`） |

**按需再加，别一次装齐**。每加一个依赖就多一个在生产环境装不上的风险，也许多一个被反爬升级打废的模块。

## 3. 判断：走「采集入库 + 本地检索」

### 为什么不直接做多源实时聚合

清单 §P1-1 写的是「插件化 + 第二通道」，那是**只加一个 API 源**的方案。现在目标升级成「自己抓」，性质变了：

| 维度 | 实时聚合（PanSou 式） | 采集入库（下个吧式） |
|---|---|---|
| 用户搜索延迟 | 等于最慢的那一源（4 秒窗口 + 后台补齐） | 本地索引，几十毫秒 |
| 源站变慢/挂掉 | 直接影响本次搜索 | 只影响库的新鲜度 |
| 反爬升级 | 实时链路当场断 | 采集任务报错，用户无感 |
| 空库风险 | 无（每次现抓） | **有，必须有冷启动兜底** |
| 能否做「全站热门」 | 不能（没有历史数据） | 能（库就是历史） |
| 我们的转存/检活 | 转存压力跟着搜索量走 | 可以先校验再上架，转存成功率更高 |

最后两行是关键：**库能沉淀，聚合不能**。我们已经有 `check.py` 判链接死活、`pan.py` 做转存——这两个能力只有在「资源先入库」的前提下才能提前跑，而不是等用户点。

### 定下来的架构

```
                 ┌──────────────────────────────┐
                 │  采集器（后台，可失败、可重试）│
                 │  collector/源A  源B  源C ...  │
                 └──────────────┬───────────────┘
                                │ 归一化 + 去重 + 打分
                                ▼
                 ┌──────────────────────────────┐
                 │  resources 表（SQLite + FTS5）│
                 │  title / url / platform / ... │
                 └──────────────┬───────────────┘
                                │ 查询（毫秒级）
                                ▼
     /api/search ──────────────► 本地检索 ──► check.py 标注 ──► /go 转存
          │
          └─ 库内结果不足时 → idatariver 补量（降级为兜底，不再是唯一通道）
```

三条硬规则：

1. **搜索链路里绝不出现外部请求**。`/api/search` 只查库 + 查 `link_check` 表，一个 `requests.get` 都不许有。这条守住，源站怎么死都不影响用户。
2. **采集是独立进程/定时任务**，不跑在 uvicorn 的 worker 里。慢、会卡、会重试，这些都不该跟 Web 进程共享生命周期。
3. **每个源独立报错、独立计时、进 `/api/health`**。清单 §P1-1 那条红线继续有效：不许静默 fallback，否则签名过期那种「日志里只剩慢」的事故会重演。

## 4. 数据模型

不用 Prisma 那套，SQLite 一张表 + 一张 FTS 表就够。**先能跑，再谈优化。**

```sql
CREATE TABLE IF NOT EXISTS resources (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  -- 去重键：platform + 归一化 share id。复用 sdk/urls.py 的解析，别再写一套正则
  dedup_key   TEXT NOT NULL UNIQUE,
  title       TEXT NOT NULL,
  platform    TEXT NOT NULL,          -- quark / baidu / ali / uc / ...
  url         TEXT NOT NULL,          -- 原始分享链接（不含提取码）
  pwd         TEXT DEFAULT '',        -- 提取码
  file_count  INTEGER DEFAULT 0,
  size_bytes  INTEGER DEFAULT 0,
  source_name TEXT NOT NULL,          -- 来自哪个采集源
  source_level INTEGER DEFAULT 3,     -- 源可信度 1~3，进排序分
  tags        TEXT DEFAULT '',        -- 逗号分隔
  -- 采集到的时间。不要拿源站上的「发布时间」当排序依据：盗版站的日期基本是编的
  collected_at INTEGER NOT NULL,
  check_state TEXT DEFAULT '',        -- 冗余 check.py 的最新结论，避免每次 JOIN
  check_at    INTEGER DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_res_platform   ON resources(platform);
CREATE INDEX IF NOT EXISTS idx_res_collected  ON resources(collected_at DESC);
CREATE INDEX IF NOT EXISTS idx_res_check      ON resources(check_state, check_at);

-- 检索用。tk 列存的是预切好的 1-gram + 2-gram，不是原文
CREATE VIRTUAL TABLE IF NOT EXISTS resources_fts USING fts5(
  title, tk, tokenize='unicode61'
);
```

`resources_fts` 的 rowid 对齐 `resources.id`（插入时显式指定 `rowid`），这样查询拿到 rowid 直接回表。

## 5. 两个已经验证过的技术点

### 5.1 中文检索：FTS5 + 1-gram/2-gram（**别用 trigram**）

先说踩到的坑。SQLite 3.53.1 的 `tokenize='trigram'` 看着最省事，实测：

```
三体       -> 0 条      ← 两字词直接搜不到
科幻小说   -> 1 条      ← 四字正常
小红书     -> 1 条
慈欣       -> 0 条      ← 又一条两字词
```

trigram 要求查询串 ≥ 3 字符。中文两字词（「三体」「慈欣」「周杰」）是最常见的搜索形态，**这一条就把方案废了**。

可行做法是自己切 gram，写入 `tk` 列，查询时同样切：

```python
def grams(text: str) -> str:
    """1-gram + 2-gram。不依赖分词词典，召回优先。"""
    text = re.sub(r"\s+", " ", text.strip().lower())
    out = set()
    for seg in text.split(" "):
        for n in (1, 2):
            for i in range(len(seg) - n + 1):
                out.add(seg[i : i + n])
    return " ".join(sorted(out))
```

实测结果（同一批数据）：

| 关键词 | trigram | 1-gram + 2-gram |
|---|---|---|
| 三体 | 0 | 1 ✅ |
| 科幻 | — | 1 ✅ |
| 慈欣 | 0 | 1 ✅ |
| 小红书 | 1 | 1 ✅ |
| 庆余年 | — | 1 ✅ |
| 运营 | — | 1 ✅ |

代价：索引膨胀约 2 倍（一行 30 字标题 → 约 60 个 gram），召回全但精确度靠后续打分补。**这个代价换「两字词能搜到」，值。**

查询时按 AND 连接各 gram：`"三" AND "体" AND "三体"`，天然实现「所有字都出现过」的模糊匹配，和用户预期一致。

### 5.2 排序：三段相加，但**不启用时间项**

照清单 §P1-2：

```
总分 = 源等级(1000/500/0) + 完整度 + 有提取码(+100) + 关键词命中位置
```

**时间项不启用**。理由清单里写过：上游 `indexedTime` 恒为空，凭空造「采集时间」当新鲜度会让排序变成噪声——采集时间只反映「我们什么时候补的货」，跟资源新旧无关。等某个源真能稳定给出可信时间再加。

## 6. 采集器怎么写

### 6.1 接口：一个函数，不是一个类

PanSou 用 `BaseAsyncPlugin` 包一大堆，那是因为 Go 侧要管并发和缓存。Python 侧采集器是**离线批量跑**的，不需要那些：

```python
# backend/app/collect/sources/base.py
from typing import Protocol


class CollectSource(Protocol):
    name: str           # 唯一标识，落库进 source_name
    level: int          # 1 最可信 ~ 3
    enabled: bool

    def fetch(self, keyword: str, limit: int = 50) -> list[dict]:
        """按关键词抓一批。返回归一化后的 dict 列表，字段见 resources 表。

        约定：
        - 不抛异常给调用方，抓不到就返回 []
        - 只返回「有网盘链接」的条目，没链接的详情页在采集阶段就丢掉
        - url 必须是能直接打开/转存的分享链接，不是详情页地址
        """
```

关键是最后一条：**我们和 PanSou 不一样，PanSou 给个详情页链接也能交差，我们要能转存**。`pan.py` 的转存流水线只认真实分享链接，详情页地址进来就是废数据。所以采集器必须「进详情页把真链接挖出来」，不能停在列表页。

### 6.2 关键词从哪来

采集是**按词抓**的，所以「采什么词」本身就是个产品问题。三个来源，从便宜到贵：

1. **站点自己的热门/最新页**（`/label/new.html`、`/label/hot.html` 这类）——不消耗搜索配额，最适合冷启动
2. **我们自己的搜索日志**（`analytics.db` 里已经有真实 query）——词准，但要等有量
3. **人工词表**（`data/keywords.txt`）——可控，适合补垂类

下个吧的 `hotwords` 配置就是这个思路（`server/api/admin/config/hotwords.ts`）。

### 6.3 采集器必须有的三件事

| 事 | 为什么 |
|---|---|
| **单源熔断** | 连续 N 次失败就停 1 小时，别让一个死源每轮都白跑一遍 |
| **限速** | 每源独立间隔（从 3~5 秒起步），别把 113 个源那套并发搬过来——那是打免费站的打法，我们只需要「慢慢攒」 |
| **落库前检活**（可选） | 复用 `check.py` 的 `check_one`，`bad` 的直接不入库。这一步能把库的干净度拉高一个档 |

## 7. 加源之前，先跑探针

`backend/scripts/probe_source.py`（这次新建的）。它在「写代码」之前把 §2 的三层判定跑一遍：

```bash
# 1) 一批域名只看可达性
python scripts/probe_source.py --hosts haisou.cc sdso.top ahhhhfs.com

# 2) 具体搜索接口，看能不能捞出网盘链接
python scripts/probe_source.py --url "https://xxx/api/search?q={kw}" --kw 三体 --show

# 3) 本机网络和线上不一样时，显式指定代理
python scripts/probe_source.py --url "..." --kw 三体 --proxy http://127.0.0.1:16796
```

输出状态：`OK` / `JS_CHALLENGE` / `CLOUDFLARE` / `NO_LINK` / `UNREACHABLE` / `TIMEOUT` / `BAD_STATUS`。

**这道工序的价值是省时间**：§2.2 那五个源，我如果先跑探针，能在一个命令里就放弃其中四个，而不是每个都去读一遍插件代码再试。

## 8. 实施顺序

| 阶段 | 做什么 | 产出判据 |
|---|---|---|
| **P1** 建库 + 检索 | `app/store.py`：建表、upsert、`search()`；`grams()` 切词 | 手插 100 条，`三体`/`科幻小说`/`庆余年` 都能搜到，耗时 < 50ms |
| **P2** 接进 `/api/search` | 本地结果优先，库内不足 `min_items` 才打 idatariver；响应加 `sources`/`partial` | 关掉 idatariver 也能搜出东西；响应里能看出「本地 12 条 + 上游 8 条」 |
| **P3** 采集器骨架 | `collect/runner.py` + 单个源的 `fetch()`，命令行可跑 | `python -m app.collect --source xxx --kw 三体` 能落库 |
| **P4** 接第二个源 | 换一种形态（第一个是 JSON 接口，第二个就用 HTML 列表 + 详情页） | 两个源的结果能靠 `dedup_key` 正确去重 |
| **P5** 定时 + 观测 | systemd timer / cron 跑采集；每源最近 20 轮 `yield/zero/fail` 进 `/api/health` | `/api/health` 能看出哪个源三天没产出 |

**先做 P1+P2，别急着写采集器。** 理由：P1/P2 决定了「库长什么样」，如果模型设计错了，采集器写得再多也是白搭；而且 P2 完成那一刻，idatariver 就从「唯一通道」变成了「兜底通道」，签名过期不再等于全站死——这是这次改造最直接的价值。

## 9. 坑

1. **trigram 两字词搜不到**。已在 §5.1 说明。这是最容易踩、且踩了之后很难归因的坑（表现是「搜某些词没结果」，不像 bug）。
2. **可达性依赖出口网络**。本机和服务器结论可能完全相反。所有源站探测必须在部署机跑，本机数据只能当参考。
3. **详情页 ≠ 分享链接**。PanSou 允许返回详情页，我们必须挖到真实分享链接，否则 `pan.py` 转存必失败。
4. **别拿采集时间当新鲜度**。§5.2。
5. **采集器不要跑在 uvicorn 进程里**。会卡住事件循环，也会在重启时把任务打断。
6. **源站会转型**。`hjzhencai` 从资源站变成影视站，代码一行没改就不工作了。所以源必须有存活观测（P5），否则「它还在库里但我们再也没补过货」这件事没人会发现。
7. **别照搬 113 个源**。PanSou 作者用 10 万行里的一半在维护这些适配，我们的价值在转存和检活，不在源的广度。**3 个稳定源 > 30 个三天就死的源。**

## 11. 修订（2026-11-20）：P0 已落地，原方案改了三处

原方案的技术验证全部有效（FTS5 + 1-gram/2-gram、探针、采集器三件事），
但冷启动路径和排序模型改了。下面只写差异，不重复上面已论证的部分。

### 11.1 三处修改

| 原方案 | 改成 | 理由 |
|---|---|---|
| P3 才做采集器 | **采集器最后做，先用影子回填** | 每次 `/api/search` 已经拿着完整 items（shareUrl/platform/sharePwd/fileCount 全齐），用完就扔。落库零额外请求、零反爬风险，词还是真实需求。判据：库里 5000 条之前不写一行采集器代码 |
| 排序**不启用**时间项 | 启用 `last_seen_at` 衰减 | 原文的理由只对"源站发布时间"成立（盗版站日期基本是编的）。`last_seen_at` 是我们自己观测到"这条最近还在上游出现"的时间，可信 |
| 只有 `resources` 一张表 | 加 `resource_hits` 聚合表 | 没有命中记录，库只是个会过期的缓存；有它才能做热榜、相关推荐、死链率看板。这是聚合器结构上给不了的东西 |

### 11.2 两条已定决策

1. **库的形态**：纯索引库（元数据 + 分享链接），不做文件镜像。点击仍走现有转存/跳转链路。
2. **取数策略**：本地库与上游**并行合并**，不是"本地不足才兜底"。理由：现网 TG 通道本来就有 4~6 秒窗口，本地查询 <50ms，并行不改变临界路径，延迟成本约等于 0。代价是上游额度照旧烧——库的价值收敛成「兜底 + 沉淀 + 可运营」，不再包括"省成本"。

> 推论：既然搜索行为本身没变化，**P2 的榜单页和资源详情页从"可做"变成"必须做"**。用户唯一能感知到"我们有个库"，就在那两个页面上。

### 11.3 P0 实现与实测

`backend/app/store.py`（新建，约 500 行）+ `backend/tests/test_store.py`（18 个用例全过）。

实际表结构比原方案多五个字段，都有明确用途：

| 字段 | 为什么 |
|---|---|
| `aliases` | 同一分享被不同帖子转发，标题各不相同。别名全部进 FTS，用户搜"三体2"和"三体 第二季"都要命中同一条 |
| `hit_count` | 冗余在主表，排序直接读。JOIN hits 表做聚合会拖死搜索 |
| `click_count` | 点击比命中更有信息量 |
| `revive_count` | `bad → ok` 的次数。比任何评分都准的"有人在持续分享"信号 |
| `archived_at` | 冷存时间。单独一列，不塞进状态——状态会被巡检改写，时间不能丢 |

去重键是 `platform:pwd_id`（`sdk/urls.py` 的 `ParsedShare`），**不是 URL 字符串**。同一条夸克资源的五种写法（带 `?pwd=`、尾斜杠、大小写域名、锚点、分享文案）必须归一成一条。

**切词有一处必须注意**：不能先按空格分段再切 n-gram。标题「三体 全集」会被切成两段，跨空格的双字 `体全` 进不了索引，用户搜「三体全集」就召不回来。所以先剥掉所有空白和标点，把文本压成连续串再切。

实测（1000 条合成数据，本机）：

| 项目 | 实测 | 判据 |
|---|---|---|
| 批量入库 1000 条 | 39ms | — |
| 检索「三体」 | 4~5ms | <50ms ✅ |
| 检索「三体全集」（跨空格） | 4ms，命中 7 条 | 必须命中 ✅ |
| 库文件体积 | 0.6MB / 1000 条 | 100 万条约 1.5GB，单文件舒适区 |

接入点是 `main.py:_export_search()`，位置**必须在 `_apply_hidden` 之后、`_public_body` 之前**：
前者保证进库的条目已经剔掉被举报的，后者一执行就把 `shareUrl` 换成 `/go/<token>` 签名串，
那之后落库的全是解不开的废数据。回填走 `BackgroundTasks`，不进响应链路。

下一步 P1 要改的是 `engine.search()` 的出口：本地结果与上游并行合并、去重键换成 `dedup_key`、
分页改为「本地取 `page*page_size+50` 条参与合并后再切片」。这三条是实现细节，不是架构变更。

## 12. 修订（2026-11-20）：`resource_hits` 加 `channel`

### 12.1 为什么现在必须加

P0 的命中只有一种来源——上游返回。P1 一上线，本地检索也会开始产生命中，两种命中会混进同一个
`count`。混了之后，"这条资源的热度是上游给的多，还是库里自己找得到"就再也分不出来，而这个区别
恰好是判断「本地检索到底有没有出力」的唯一依据。

**这个数据补不回来**：113 条时的迁移是秒级，10 万条时就得停机重写百万行。

### 12.2 结构变化

```sql
-- 之前：PRIMARY KEY (resource_id, query, day)
CREATE TABLE resource_hits (
    resource_id INTEGER NOT NULL,
    query       TEXT    NOT NULL,
    day         INTEGER NOT NULL,
    channel     TEXT    NOT NULL DEFAULT 'upstream',   -- upstream / local
    count       INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (resource_id, query, day, channel)
);
```

`channel` 只认两个值，`record_hits()` 里做白名单归一，传别的值一律按 `upstream` 算。**不许让它
变成一个自由字段**——写错一个值就等于凭空多出一条统计口径，比少一个口径坏得多。

### 12.3 迁移规则

`store.init()` 里 `_migrate()` 在 `executescript(_SCHEMA)` **之前**跑，靠 `PRAGMA table_info`
判断有没有 `channel` 列，没有就 `RENAME → CREATE → INSERT SELECT → DROP → CREATE INDEX`。

三条必须守住：

1. **迁移必须在建表之前**。建表语句全是 `IF NOT EXISTS`，先执行建表会让老结构蒙混过关，
   迁移从此再也不会发生——而且不会报错。
2. **`CREATE INDEX` 必须排在 `DROP TABLE` 之后**。索引跟着旧表走，反过来写的话同名索引还在，
   `IF NOT EXISTS` 会静默跳过，新表永远没有索引。
3. **历史命中一律归 `upstream`**。这不是猜测：那些数据产生时本地检索还不存在。

### 12.4 观测变化

`store.stats()` 的 `hits_7d` 保留为**总和**（不破坏现有消费方），新增分解：

```json
"hits_7d": 299,
"hits_7d_by_channel": {"upstream": 299}
```

P1 上线后，`local` 这一项从 0 变成非 0，就说明本地库真的在出结果了。**这是本地检索是否生效的
唯一硬指标**，比看日志可靠。

## 13. 修订（2026-11-20）：搭车的请求不回填

### 13.1 问题

`singleflight` 只让第一个请求（leader）真正打上游，其余的（follower）等它的结果，并在响应里标
`shared=True`。但出口 `_export_search` 的回填是无条件的，于是 follower 拿着 leader 的同一批
items 又走了一遍 `upsert_many` + `record_hits`。

实测（同一批 10 条，1 次上游调用 + 2 个搭车）：

| 请求 | total | hits_7d |
|---|---|---|
| leader | 10 | 10 |
| follower #1 | 10 | **20** |
| follower #2 | 10 | **30** |

### 13.2 为什么不能当成"数字好看不好看"

热度有两个真实用途：P1 排序的一个因子、热榜的唯一依据。而搭车**恰好集中在热门词被多人同时搜**
的场景上——偏差不是均匀噪声，是系统性地往热榜头部堆：一个词越热、并发越高，放大倍数越大。
更极端的情况是脚本并发刷同一个词：一次上游成本都没多花，热度却能刷到榜首。单飞防住了钱，漏了账。

### 13.3 修法

```python
if LIBRARY_ON and not body.get("shared"):
    ...
```

只有三行，理由也简单：**leader 已经记过这一批，follower 既没打上游也没拿到不同结果。**

不做"按 1/N 记"的原因：出口处不知道 N 是多少（follower 可能还在陆续到达），而且这一批到底算
几次需求，本来就该由 leader 独自承担。

**L2 缓存命中仍然记**（它不带 `shared`）。那是用户隔了一段时间真的又搜了一次，属于真实需求；
要和"同一瞬间同一个请求的多份副本"区分开。

唯一代价：leader 的请求若被客户端提前掐断，`BackgroundTasks` 可能不执行，这一批就没记上。
概率很低，且下次搜同一个词会补上。

### 13.4 回归用例

`tests/test_export_ingest.py`（5 个）：leader 记、follower 不记、缓存命中照记、
`LIBRARY_ON=False` 不写、入库的是原始链接不是 `/go/<token>`。

判据一句话：3 个同键请求跑完，`total` 和 `hits_7d` 都应该还是 10。

## 14. 决策（2026-11-20）：P1 冻结，等库有量再启用

### 14.1 决定

本地检索（P1：本地与上游并行合并）**暂不启用**，等资源库链接达到一定规模后再接进搜索链路。

理由成立：现在库才 120 多条，本地检索上线只会是"本地 0~3 条 + 上游 20 条"，
用户感知不到差别，却要为此改合并逻辑、加去重键、动分页窗口——改动面不小，
收益接近于零。**库的价值和库的厚度成正比，薄的时候接进去只是给自己加复杂度。**

### 14.2 "一定数量"不能用条数定，要用覆盖率定

按条数定是错的：**5000 条长尾货可能一条热门词都盖不住。** 用户搜的是头部那几个词，
库再厚，头部覆盖不住就是没用。

判据改成一条：

> 取 `analytics.db` 里真实出现过的 top 100 query，离线跑 `store.search(q)`，
> **能返回 ≥3 条结果的 query 占比 ≥ 60%** 时，再开 P1。

这条判据测的是"库能不能接住真实需求"，不是"库有多少行"。达到这条线再上 P1，
用户体感是"结果变全了"，不是"结果变少了"。

### 14.3 冻结期间该做的事

| 优先级 | 事项 | 为什么现在做 |
|---|---|---|
| 1 | 同步 `link_check` 的既有结论进库 | 8450 条检活结论躺在另一个库里，库内却全是 `unknown`。零成本，让排序的可用性维度立刻能用 |
| 2 | 只读库查询端点（`/admin/api/library/list`） | 冻结期"库在长什么"是唯一能观察的东西，没有它只能看一个总数 |
| 3 | 采集器补长尾 | 回填只吃真实流量，涨得慢；但**先不动**，等覆盖率看板出来再决定缺哪一块 |

P1 的代码一行不动，`store.search()` 已实现且有测试，随时可以接上。

## 15. 人工收集表导入（2026-11-20）

### 15.1 为什么先做解析层

"上传腾讯文档 → 提取表格里的网盘链接"这件事有两层：**取数**（拿到表格内容）和
**解析**（行 → 资源）。取数方式未定（连接器 / 导出接口 / 手动下载），解析层不该绑死它。

所以 `app/intake.py` 的输入是 `list[list[str]]`，与取数方式无关。取数换了，解析一行不用改。

链接提取和提取码清洗复用 `search.clean`（照 pansou `regex_util.go` 逐行翻译的，
覆盖九种网盘）。这里只补表格语义。

### 15.2 表格特有的三个坑（文案提取那套解决不了）

| 坑 | 表现 | 处理 |
|---|---|---|
| **提取码单独占一列**，值就是 `1234` | `clean.password_for` 靠"提取码："关键词认码，对独立列完全失效 → 整表无码 | 先认表头，没有表头就按"整列 ≥60% 是 4 位码"推断 |
| **一行多链接共用标题** | 要是每条链接各配一个标题，会拿到一堆垃圾 | 标题列优先，其次行内最长的像标题的片段 |
| **整行是一段分享文案** | 没有任何单元格是干净标题 | 整行清洗后取标题；清洗完只剩码就用占位并计入 `untitled` |

### 15.3 提取码归属：从码出发，不是从链接出发

这是本模块唯一一个"写错了会害用户"的地方。

```
"三体 https://pan.quark.cn/s/q1 提取码 1111 https://pan.baidu.com/s/1q2"
```

- 复用 `clean.password_for` → 百度那条也会拿到 1111（它就近取不到时退回整段扫描）。
  用户拿错码去存，得到"提取码错误"，**比不给码更糟**。
- 复用 `clean.extract_code_near` → 它也有一条"上下文很短就把整段当窗口"的规则，
  表格一行本来就短，同样跨链接。

所以自己实现 `assign_codes()`：**每个码分给离它最近的链接，一个码只给一条**。
等距时（1111 到夸克、百度都是 5 个字符）按"码在链接右侧优先"——中文里
"链接 xxx 提取码 1234"是绝对主流写法。宁可给空，也不给错码。

### 15.4 每天监控不需要 diff

导入是幂等的：`dedup_key` 相同的资源只更新 `last_seen_at`。所以"监控文档有没有更新"
就是**每天跑一次导入，看新增数**：

| 报告 | 含义 |
|---|---|
| 新增 0、更新 12 | 表没变 |
| 新增 3、更新 12 | 表里加了 3 条新的 |
| 可入库 0、跳过 20 | 列结构变了，或链接全被挡 |

不需要存文档快照、不需要算 hash、不需要 diff 表。

### 15.5 已知边界

- **123 / 天翼的链接会被挡**（提取得出，但不在 `sdk/urls.py` 的转存白名单）。
  这是口径不是 bug：库里的链接最终要走 `/go` 转存，没有适配器的平台存进去也点不开。
  要放开就得先让 `/go` 在无适配器时直接 302 到原链接——那是另一个决定。
- **无标题的条目用占位名**（`quark 分享 abc123`），能点开但搜不到。报告里会计数。

### 15.6 用法

```bash
cd backend
.venv/Scripts/python.exe scripts/import_doc.py --file 资源表.csv --dry-run   # 先看
.venv/Scripts/python.exe scripts/import_doc.py --file 资源表.csv --name "老王的表"
```
